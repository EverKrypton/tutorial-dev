Git no es GitHub

Se confunden todo el tiempo, pero son cosas distintas:

  • Git es un programa que corre en tu computadora. Guarda el historial de tu proyecto en una carpeta oculta llamada .git. Funciona sin internet.
  • GitHub es un sitio web donde puedes guardar una copia de ese historial. Es como YouTube, pero para repositorios. También existen GitLab y Bitbucket.
En simple

Git es el «guardar partida» de un videojuego: puedes volver a cualquier momento. GitHub es subir ese save a la nube para jugar desde otra consola y enseñárselo a tus amigos.

Instalar y configurar

Comprueba si ya lo tienes:

bash
git --version

Si no aparece una versión, instálalo desde git-scm.com (o con brew install git en macOS, sudo apt install git en Ubuntu).

Después, dile quién eres. Esto se guarda en cada commit:

bash
git config --global user.name "Tu Nombre"
git config --global user.email "tu@correo.com"

Y crea una cuenta en github.com. Si quieres usar la terminal sin pelear con contraseñas, instala GitHub CLI y ejecuta:

bash
gh auth login

Elige GitHub.com, HTTPS y autenticación por navegador. Eso configura tus credenciales para git push.

Tu primer repositorio

Un repositorio es una carpeta que Git está vigilando. Vamos a crear uno con tu tarjeta del capítulo anterior:

  1. Entra a la carpeta del proyecto

    bash
    cd mi-tarjeta

  2. Inicia el repositorio

    bash
    git init

    Crea la carpeta .git. A partir de ahora Git puede ver los cambios.

  3. Mira el estado

    bash
    git status

    Te dice qué archivos son nuevos, cuáles cambiaron y qué está listo para guardar. Úsalo todo el tiempo; es tu brújula.

  4. Prepara y guarda

    bash
    git add .
git commit -m "Primera versión de mi tarjeta"

    git add . mete todos los cambios en la «caja» y git commit toma la foto. Son dos pasos a propósito: puedes elegir qué entra.

Ver el historial:

bash
git log --oneline

Deberías ver algo como a1b2c3d Primera versión de mi tarjeta. Ese código raro es el identificador del commit. Git lo genera solo.

El archivo .gitignore

No todo debe guardarse. Crea un archivo llamado .gitignore en la raíz y escribe lo que quieres excluir:

gitignore
node_modules/
.env
.env.local
.DS_Store
dist/
Nunca subas secretos

Claves de API, contraseñas y archivos .env no van al repositorio, ni siquiera si es privado. Si ya subiste una clave, bórrala del código y cámbiala: el historial la conserva.

Commits que sirven

Un commit es una foto con una nota. La nota debería explicar qué cambió y por qué, no «cosas».

Mal

git commit -m "cambios"

Bien

git commit -m "Agrega botón de modo oscuro en la tarjeta"

Una convención muy extendida es empezar con un tipo:

PrefijoCuándo
feat:Una funcionalidad nueva
fix:Corrige un error
docs:Solo documentación
style:Formato, sin cambiar comportamiento
refactor:Reorganiza sin agregar funciones
chore:Tareas de mantenimiento

Ejemplo: feat: agrega formulario de contacto. Commits pequeños y frecuentes son más fáciles de entender y de deshacer que uno gigante al final del día.

Ramas

Una rama es una línea de trabajo paralela. La principal suele llamarse main. Si quieres probar algo sin romper lo que funciona, creas una rama:

bash
git switch -c diseno-nuevo   # crea y entra a la rama
# ...trabajas, agregas y commiteas...
git switch main              # vuelves a la principal
git merge diseno-nuevo       # traes los cambios

Si las dos ramas tocaron la misma línea, Git te avisa de un conflicto. No es un desastre: abre el archivo, verás marcas como estas:

texto
<<<<<<< HEAD
color: azul;
=======
color: verde;
>>>>>>> diseno-nuevo

Elige qué queda (o combina), borra las marcas, guarda y haz commit. Git no decide por ti porque no sabe qué querías.

Subir a GitHub

Crea un repositorio vacío en GitHub. No marques «Add a README» si ya tienes archivos locales. Luego conecta tu carpeta:

bash
git remote add origin https://github.com/TU-USUARIO/mi-tarjeta.git
git branch -M main
git push -u origin main

La primera vez te pedirá autenticarte. Con gh auth login ya hecho, debería funcionar directo. A partir de ahí, cada vez que quieras subir cambios:

bash
git add .
git commit -m "fix: corrige el contraste del botón"
git push

Y si trabajas en otra computadora o quieres una copia:

bash
git clone https://github.com/TU-USUARIO/mi-tarjeta.git

Pull requests

Un pull request (PR) es una propuesta: «tengo estos cambios en mi rama, ¿los integramos?». En proyectos de equipo permite revisar antes de mezclar. En tus proyectos personales también sirve para verte el código con calma.

El flujo típico:

  1. Creas una rama: git switch -c mi-cambio.
  2. Haces commits.
  3. Subes la rama: git push -u origin mi-cambio.
  4. GitHub te muestra un botón «Compare & pull request».
  5. Escribes qué cambia y por qué. Pides revisión si hay equipo.
  6. Se mezcla con main.
Vercel se conecta aquí

Cuando conectas un repositorio a Vercel, cada push a main produce un deploy de producción, y cada PR produce una URL de preview. Vas a verlo en el siguiente capítulo.

Deshacer sin pánico

Antes de cualquier comando de deshacer, ejecuta git status y git log --oneline. Saber dónde estás evita el 90% de los desastres.

SituaciónComandoQué hace
Cambiaste un archivo y te arrepientesgit restore archivoVuelve a la última versión guardada
Quieres sacar un archivo del staginggit restore --staged archivoLo deja modificado pero sin preparar
El último commit está malgit commit --amendLo reemplaza (no lo uses si ya lo subiste)
Quieres deshacer un commit ya publicadogit revert <hash>Crea un commit nuevo que revierte
Guardar cambios sin commiteargit stashLos aparta temporalmente; git stash pop los devuelve
Cuidado con reset --hard

git reset --hard borra cambios sin preguntar. No lo uses hasta entenderlo. Para deshacer algo que ya subiste, git revert es casi siempre la opción segura.

Buenas costumbres

  • Un commit = una idea. No mezcles «arreglo el botón» con «cambio todo el diseño».
  • Haz git pull antes de empezar si trabajas con más gente.
  • Nunca subas node_modules, .env ni archivos generados.
  • Escribe un README con qué es el proyecto y cómo correrlo.
  • Usa ramas para experimentos. main debería funcionar siempre.
  • Si un repo es público, agrega una licencia (MIT es la más simple).
