Qué es un servidor, de verdad

Cuando abres una web, tu navegador hace una petición y alguien responde. Ese «alguien» es un programa que está corriendo en una máquina, esperando. Eso es un servidor: un programa que escucha en un puerto y contesta.

No es una máquina mágica. Es esto:

javascript
import { createServer } from "node:http";

const server = createServer((req, res) => {
  res.writeHead(200, { "Content-Type": "text/plain; charset=utf-8" });
  res.end("Hola desde el servidor");
});

server.listen(3000, () => {
  console.log("Escuchando en http://localhost:3000");
});

Guárdalo como server.mjs y ejecuta node server.mjs. Abre http://localhost:3000 y ahí está: tu primer servidor. Diez líneas.

En simple

Un servidor es un camarero que no se cansa. Está parado en la puerta (el puerto) esperando pedidos. Cada vez que alguien pide algo, mira qué pidió, va a la cocina y trae la respuesta. Nunca cierra el restaurante.

HTTP en una servilleta

Todo lo que pasa entre navegador y servidor son cuatro cosas:

PiezaEjemploQué es
MétodoGET, POST, PUT, DELETEQué quieres hacer
Ruta/api/tareas/3Sobre qué
CabecerasContent-Type: application/jsonMetadatos de la petición
Cuerpo{"titulo":"Comprar pan"}Los datos (en POST/PUT)

Y la respuesta tiene lo mismo: un código de estado, cabeceras y cuerpo.

CódigoSignificaCuándo
200OKTodo bien
201CreadoAcabas de insertar algo
204Sin contenidoBorraste algo, no hay cuerpo
400Petición inválidaFaltan datos o están mal
401No autenticadoNo has iniciado sesión
403ProhibidoEstás dentro, pero no puedes
404No encontradoEsa ruta no existe
500Error del servidorTu código falló

Regla que casi nadie sigue al principio: el código de estado es parte de la respuesta. Si algo falla y devuelves 200 con un mensaje de error dentro, el cliente no puede distinguir el éxito del fallo.

Tu primera API con Hono

Escribir rutas a mano con node:http funciona, pero se vuelve tedioso. Un framework pequeño te ahorra el parseo y el enrutado. Hono es ligero, moderno y corre en Node, Bun, Deno y Vercel.

bash
mkdir mi-api && cd mi-api
npm init -y
npm install hono @hono/node-server
npm pkg set type=module
javascript
// server.mjs
import { Hono } from "hono";
import { serve } from "@hono/node-server";

const app = new Hono();

// datos en memoria, para empezar
let tareas = [
  { id: 1, titulo: "Aprender HTTP", hecha: true },
  { id: 2, titulo: "Montar la API", hecha: false },
];

app.get("/api/tareas", (c) => c.json(tareas));

app.get("/api/tareas/:id", (c) => {
  const tarea = tareas.find((t) => t.id === Number(c.req.param("id")));
  if (!tarea) return c.json({ error: "No existe" }, 404);
  return c.json(tarea);
});

app.post("/api/tareas", async (c) => {
  const body = await c.req.json();
  if (!body?.titulo) return c.json({ error: "Falta el título" }, 400);
  const nueva = { id: Date.now(), titulo: body.titulo, hecha: false };
  tareas.push(nueva);
  return c.json(nueva, 201);
});

app.delete("/api/tareas/:id", (c) => {
  const id = Number(c.req.param("id"));
  tareas = tareas.filter((t) => t.id !== id);
  return c.body(null, 204);
});

serve({ fetch: app.fetch, port: 3000 }, (info) => {
  console.log(`API en http://localhost:${info.port}`);
});

Pruébala sin escribir nada de interfaz:

Por qué curl y no el navegador

El navegador solo hace GET cuando escribes una URL. Para probar POST, PUT o DELETE necesitas curl, Postman o un formulario. Aprender curl te hace independiente de cualquier herramienta gráfica.

Guardar de verdad: un archivo JSON

Los datos en memoria desaparecen al reiniciar. Antes de meter una base de datos, aprende a persistir en un archivo: es suficiente para aprender y para muchas herramientas pequeñas.

javascript
import { readFile, writeFile } from "node:fs/promises";

const RUTA = "./tareas.json";

async function leer() {
  try {
    return JSON.parse(await readFile(RUTA, "utf8"));
  } catch {
    return [];
  }
}

async function guardar(tareas) {
  await writeFile(RUTA, JSON.stringify(tareas, null, 2));
}

Y en cada ruta: const tareas = await leer() al empezar, await guardar(tareas) al terminar. Cuando el proyecto crezca, cambias esas dos funciones por consultas a SQLite o Postgres y el resto del código no se entera.

Conectar una web a tu servidor

Aquí está el error que frena a todo el mundo la primera vez. Tienes la API en el puerto 3000 y la web en el 5173. La web hace fetch("http://localhost:3000/api/tareas") y el navegador responde:

error
Access to fetch at 'http://localhost:3000/api/tareas'
from origin 'http://localhost:5173' has been blocked by CORS policy

CORS es una regla del navegador: una página solo puede leer respuestas de otro origen si ese servidor lo autoriza explícitamente. No es un bug: es una protección.

La solución está en el servidor, no en el cliente. Con Hono:

javascript
import { cors } from "hono/cors";

app.use("/api/*", cors({
  origin: ["http://localhost:5173", "https://mi-web.vercel.app"],
  allowMethods: ["GET", "POST", "DELETE"],
}));
Nunca uses "*" en producción

origin: "*" permite que cualquier web lea tu API. Sirve para practicar, pero si hay datos de usuarios o escritura, lista los orígenes permitidos. Y recuerda: si hay cookies o sesión, además necesitas credentials: true y un origen exacto, nunca *.

El cliente, paso a paso

javascript
const API = "http://localhost:3000/api";

async function listar() {
  const res = await fetch(`${API}/tareas`);
  if (!res.ok) throw new Error(`Error ${res.status}`);
  return res.json();
}

async function crear(titulo) {
  const res = await fetch(`${API}/tareas`, {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ titulo }),
  });
  if (!res.ok) {
    const { error } = await res.json();
    throw new Error(error);
  }
  return res.json();
}

Cuatro reglas para no sufrir:

  • Comprueba res.ok siempre. fetch no lanza error en un 404.
  • Manda Content-Type: application/json en los POST con cuerpo JSON.
  • Serializa con JSON.stringify y lee con res.json().
  • Envuelve todo en try/catch y muestra un estado de error en la interfaz.

Una web mínima que consume la API

Sin frameworks, para ver el circuito completo:

html
<!doctype html>
<html lang="es">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>Tareas</title>
</head>
<body>
  <main>
    <h1>Tareas</h1>
    <form id="form">
      <input id="titulo" placeholder="Nueva tarea" required>
      <button>Añadir</button>
    </form>
    <ul id="lista"></ul>
    <p id="estado"></p>
  </main>
  <script type="module" src="app.js"></script>
</body>
</html>
javascript
const API = "http://localhost:3000/api";
const lista = document.querySelector("#lista");
const estado = document.querySelector("#estado");

async function pintar() {
  estado.textContent = "Cargando…";
  try {
    const res = await fetch(`${API}/tareas`);
    if (!res.ok) throw new Error("No se pudo cargar");
    const tareas = await res.json();
    lista.innerHTML = tareas
      .map((t) => `<li>${t.titulo}</li>`)
      .join("");
    estado.textContent = "";
  } catch (e) {
    estado.textContent = e.message;
  }
}

document.querySelector("#form").addEventListener("submit", async (e) => {
  e.preventDefault();
  const input = document.querySelector("#titulo");
  await fetch(`${API}/tareas`, {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ titulo: input.value }),
  });
  input.value = "";
  pintar();
});

pintar();

Con esto tienes el circuito completo: formulario → fetch → API → JSON → render. Todo lo demás que construyas encima es la misma idea con más piezas.

Cuidado con innerHTML

innerHTML con texto que viene del usuario es una puerta abierta a XSS: si alguien escribe <img src=x onerror=alert(1)>, se ejecuta. Para datos reales usa textContent o crea nodos con document.createElement.

Poner el servidor en internet

En tu computadora el servidor vive en localhost, que solo existe para ti. Para que el mundo lo alcance hay tres caminos:

OpciónCuándoEsfuerzo
Serverless (Vercel)API pequeña, tráfico variableMínimo
VPS con systemd + nginxControl total, websockets, procesos largosMedio
Plataforma gestionada (Railway, Render, Fly)Quieres un servidor sin administrarloBajo

Opción A: Vercel, sin servidor propio

Con Next.js, un archivo en app/api/tareas/route.ts ya es una API. No hay que abrir puertos ni configurar nada:

typescript
// app/api/tareas/route.ts
export async function GET() {
  return Response.json([{ id: 1, titulo: "Aprender" }]);
}

export async function POST(req: Request) {
  const body = await req.json();
  if (!body?.titulo) {
    return Response.json({ error: "Falta el título" }, { status: 400 });
  }
  return Response.json({ id: Date.now(), ...body }, { status: 201 });
}

Queda en https://tu-proyecto.vercel.app/api/tareas. Como la web y la API comparten dominio, CORS desaparece. Esa es la razón principal por la que la gente empieza con Next.

Opción B: un VPS

Pasos reales, en orden:

  1. Entra por SSH

    ssh root@tu-ip. Actualiza: apt update && apt upgrade -y.

  2. Crea un usuario sin root

    adduser mara y usermod -aG sudo mara. Trabajar como root todo el día es pedir un accidente.

  3. Instala Node

    Con nvm o con el paquete de NodeSource. Comprueba con node -v.

  4. Sube el código

    git clone https://github.com/tu-usuario/mi-api.git y npm install --omit=dev.

  5. Regístralo como servicio

    Un archivo en /etc/systemd/system/mi-api.service con ExecStart=/usr/bin/node /home/mara/mi-api/server.mjs y Restart=always.

  6. Pon nginx delante

    nginx escucha en el puerto 80/443, termina el HTTPS y reenvía a localhost:3000. Tu app nunca se expone directamente.

  7. HTTPS con certbot

    certbot --nginx -d api.tudominio.com. Renueva solo.

nginx
server {
  server_name api.tudominio.com;

  location / {
    proxy_pass http://127.0.0.1:3000;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-Proto $scheme;
  }
}
Por qué nginx delante

Node no debería enfrentarse solo a internet: nginx maneja TLS, comprime, sirve archivos estáticos rápido y aguanta picos. Además te deja tener varias apps en el mismo servidor, cada una en su subdominio.

Lo mínimo de seguridad

  • Nunca subas .env al repositorio. Las claves viven en variables de entorno del servidor.
  • Valida todo lo que llega: si esperas un número, comprueba que lo sea.
  • No devuelvas el error interno al cliente. Registra el detalle, responde algo genérico.
  • Limita el tamaño del cuerpo y el número de peticiones si la API es pública.
  • Actualiza dependencias: npm audit.
  • Si hay usuarios, contraseñas con hash (bcrypt/argon2), nunca en texto plano.

Ejercicios

Ejercicio 01

Servidor de veinte líneas

Escribe un servidor con node:http que responda «Hola» en /, un JSON en /api/hora con la fecha actual, y un 404 en cualquier otra ruta. Pruébalo con curl.

Ejercicio 02

CRUD completo

Convierte el ejemplo de Hono en un CRUD de notas con persistencia en JSON: listar, ver una, crear, editar (PUT) y borrar. Prueba los cinco verbos con curl antes de tocar la interfaz.

Ejercicio 03

Rompe el CORS a propósito

Sirve la web en un puerto y la API en otro, sin configurar CORS. Lee el error completo del navegador. Después añade el middleware y comprueba que desaparece. Entender el error vale más que copiar la solución.

Ejercicio 04

De localhost a internet

Despliega la API en Vercel como route handler y apunta la web a la URL pública. Comprueba que ya no hay CORS porque comparten origen. Después intenta la misma API en un VPS con systemd y nginx y compara el esfuerzo.

Lo importante

Una web y un servidor son dos programas hablando por HTTP. Si entiendes método, ruta, cabecera, cuerpo y código de estado, entiendes el 90% de internet. El resto son herramientas encima de esa misma idea.
