Qué añade Next sobre React

React te da componentes. No te da rutas, ni datos en el servidor, ni optimización de imágenes, ni un lugar donde poner una API. Next.js es React más todo eso, con convenciones claras.

En simple

React es el motor. Next es el coche completo: motor, volante, ruedas y maletero. Puedes montarlo tú pieza a pieza, o arrancar y conducir.

Crear el proyecto

bash
npx create-next-app@latest mi-sitio
# responde: TypeScript sí, ESLint sí, Tailwind no (aquí usamos CSS propio)
cd mi-sitio
npm run dev

La estructura que importa:

estructura
app/
├── layout.tsx        # envuelve TODAS las páginas
├── page.tsx          # la ruta "/"
├── globals.css
├── about/
│   └── page.tsx      # la ruta "/about"
├── blog/
│   ├── page.tsx      # "/blog"
│   └── [slug]/
│       └── page.tsx  # "/blog/cualquier-cosa"
└── api/
    └── hola/
        └── route.ts  # "/api/hola"

Una carpeta es una ruta. Un page.tsx es la página. No hay archivo de rutas que mantener.

Rutas y layout

layout.tsx es el marco: se renderiza una vez y envuelve cada página. Ahí van la navegación, el pie y el <html>.

tsx
// app/layout.tsx
import Link from "next/link";
import "./globals.css";

export const metadata = {
  title: "Mi sitio",
  description: "Aprendiendo Next.js",
};

export default function RootLayout({ children }: { children: React.ReactNode }) {
  return (
    <html lang="es">
      <body>
        <header>
          <Link href="/">Inicio</Link>
          <Link href="/blog">Blog</Link>
        </header>
        <main>{children}</main>
      </body>
    </html>
  );
}

Para navegar se usa <Link>, nunca <a> para rutas internas: Link precarga y navega sin recargar la página.

Componentes de servidor: la diferencia clave

En el App Router, los componentes son de servidor por defecto. Eso significa que su código nunca llega al navegador: se ejecuta en el servidor y solo se envía el HTML resultante.

tsx
// app/page.tsx — componente de servidor
import { readFile } from "node:fs/promises";

export default async function Home() {
  const posts = JSON.parse(await readFile("./data/posts.json", "utf8"));

  return (
    <ul>
      {posts.map((p) => (
        <li key={p.slug}>{p.titulo}</li>
      ))}
    </ul>
  );
}

Ese readFile solo puede existir en el servidor. En un componente de cliente daría error, porque el navegador no tiene acceso a los archivos del proyecto.

Cuándo necesitas "use client":

  • Usas useState o useEffect.
  • Escuchas eventos (onClick, onChange).
  • Usas APIs del navegador (window, localStorage).

Todo lo demás se queda en el servidor. Eso hace el sitio más rápido: menos JavaScript enviado, menos trabajo en el teléfono.

tsx
"use client";

import { useState } from "react";

export function Contador() {
  const [n, setN] = useState(0);
  return <button onClick={() => setN(n + 1)}>{n}</button>;
}

Leer datos

Dos formas, y conviene saber cuándo usar cada una.

Estático: en el build

Si los datos no cambian, se generan una vez y se sirven desde la CDN. Es lo más rápido posible.

tsx
export default async function Pagina() {
  const res = await fetch("https://api.ejemplo.com/datos", {
    next: { revalidate: 3600 }, // se refresca cada hora
  });
  const datos = await res.json();
  return <pre>{JSON.stringify(datos, null, 2)}</pre>;
}

Dinámico: en cada petición

tsx
export const dynamic = "force-dynamic";

export default async function Hora() {
  return <p>{new Date().toLocaleString("es-ES")}</p>;
}

Rutas con parámetros

tsx
// app/blog/[slug]/page.tsx
export default async function Post({
  params,
}: {
  params: Promise<{ slug: string }>;
}) {
  const { slug } = await params;
  const post = await getPost(slug);

  if (!post) notFound();

  return (
    <article>
      <h1>{post.titulo}</h1>
      <div dangerouslySetInnerHTML={{ __html: post.html }} />
    </article>
  );
}

Una API en el mismo proyecto

Un route.ts es una función que recibe una petición y devuelve una respuesta. El nombre del archivo determina la ruta.

ts
// app/api/tareas/route.ts
import { NextResponse } from "next/server";

let tareas = [{ id: 1, titulo: "Aprender Next" }];

export async function GET() {
  return NextResponse.json(tareas);
}

export async function POST(req: Request) {
  const body = await req.json();
  if (!body?.titulo) {
    return NextResponse.json({ error: "Falta el título" }, { status: 400 });
  }
  const nueva = { id: Date.now(), titulo: body.titulo };
  tareas.push(nueva);
  return NextResponse.json(nueva, { status: 201 });
}
Ojo con el estado en memoria

En serverless, cada instancia tiene su propia memoria y puede apagarse. Un array en una variable sirve para aprender, pero no para producción: usa una base de datos (Postgres, SQLite, KV) o un servicio externo.

Formularios con server actions

Next permite llamar al servidor desde un formulario sin escribir un endpoint a mano:

tsx
// app/contacto/page.tsx
import { revalidatePath } from "next/cache";

async function enviar(formData: FormData) {
  "use server";
  const mensaje = String(formData.get("mensaje") ?? "").trim();
  if (mensaje.length < 5) return;

  await guardarMensaje(mensaje);
  revalidatePath("/contacto");
}

export default function Contacto() {
  return (
    <form action={enviar}>
      <textarea name="mensaje" required minLength={5} />
      <button>Enviar</button>
    </form>
  );
}

La función marcada con "use server" se ejecuta en el servidor aunque la llames desde el formulario. Ese es el mecanismo que hace que el formulario funcione incluso sin JavaScript.

SEO y metadatos

Cada página puede exportar sus metadatos. Next los convierte en etiquetas del <head>:

tsx
import type { Metadata } from "next";

export const metadata: Metadata = {
  title: "Mi primera página",
  description: "Un curso para aprender a publicar en la web.",
  openGraph: {
    title: "Mi primera página",
    images: ["/og.png"],
  },
};

Y para rutas dinámicas, una función que recibe los parámetros:

tsx
export async function generateMetadata({ params }) {
  const { slug } = await params;
  const post = await getPost(slug);
  return { title: post.titulo, description: post.resumen };
}

Imágenes y fuentes

Dos componentes que sustituyen a lo que antes hacías a mano:

tsx
import Image from "next/image";
import { GeistSans } from "geist/font/sans";

<Image src="/foto.jpg" alt="Descripción real" width={800} height={600} />

<html className={GeistSans.variable}>

next/image genera varios tamaños, sirve el adecuado y evita el salto de layout. next/font descarga la tipografía en el build: cero peticiones a Google y cero parpadeo.

Publicar

El flujo completo, sin servidor propio:

  1. Sube a GitHub

    git init && git add -A && git commit -m "inicio" y crea el repo.

  2. Importa en Vercel

    Add New → Project → elige el repo. Detecta Next solo.

  3. Deploy

    Te da una URL. Cada push a main publica; cada PR genera un preview.

  4. Variables de entorno

    Settings → Environment Variables. Nunca en el código.

Nunca pongas secretos en el cliente

En Next, una variable con prefijo NEXT_PUBLIC_ termina en el JavaScript que descarga el visitante. Solo úsalo para cosas públicas (una URL de API, un id de analytics). Las claves van sin prefijo y se leen solo en el servidor.

Ejercicios

Ejercicio 01

Tres rutas

Crea /, /sobre-mi y /blog con un layout común. Comprueba que la navegación no recarga la página (mira la pestaña Network).

Ejercicio 02

Un blog desde archivos

Guarda tres posts en content/posts/*.json. Crea /blog que los liste y /blog/[slug] que muestre uno. Todo en componentes de servidor.

Ejercicio 03

API y cliente

Añade /api/tareas con GET y POST. Consúmela desde un componente de cliente con useState y useEffect. Observa que no hay CORS porque comparten dominio.

Ejercicio 04

Deploy real

Sube el proyecto a GitHub y despliégalo en Vercel. Añade un dominio propio si tienes uno y comprueba el certificado HTTPS.

Lo importante

La idea que hace distinto a Next: el servidor y el cliente viven en el mismo proyecto, y tú decides qué se ejecuta dónde. Esa decisión es la que separa una web rápida de una lenta.
