Qué es un agente#

Ya usaste agentes sin darte cuenta: el modo Plan y el modo Build son dos agentes distintos con instrucciones y permisos distintos. Crear el tuyo es escribir un archivo que define cuatro cosas:

  1. Quién es: un nombre y una descripción.
  2. Cómo piensa: un prompt de sistema con su rol y sus reglas.
  3. Qué puede hacer: qué herramientas tiene y cuáles requieren permiso.
  4. Con qué modelo: opcionalmente, uno distinto al global.
En simple

Un agente es un empleado con un puesto de trabajo escrito. Su archivo dice: «te llamas Revisor, tu trabajo es leer código y señalar problemas, no puedes editar archivos, y si algo no está claro preguntas». Eso es todo.

Primarios y subagentes#

TipoCómo se usaEjemplo
PrimarioHablas con él directamente; cambias con TabBuild, Plan, un agente «profesor»
SubagenteLo invoca otro agente o lo mencionas con @Un revisor, un investigador, un tester

Los subagentes son la pieza más subestimada. Trabajan en su propio contexto, hacen una tarea acotada y devuelven un resumen. Eso evita que la conversación principal se llene de detalles irrelevantes.

Crear el tuyo#

Tienes dos caminos. El asistente interactivo:

bash
opencode agent create

Te pregunta dónde guardarlo, qué debe hacer, qué permisos tiene y con qué modelo. Al final escribe el archivo.

O el camino directo: creas el archivo a mano. Para un agente de proyecto:

bash
mkdir -p .opencode/agents
touch .opencode/agents/profesor.md

Para uno global, en ~/.config/opencode/agents/. El nombre del archivo es el nombre del agente.

El archivo completo#

Este es un agente que explica código como si tuvieras doce años, sin editar nada:

markdown
---
description: Explica código y conceptos de programación en español, con analogías simples, sin modificar archivos. Úsalo cuando el usuario pida entender algo o aprender.
mode: subagent
model: anthropic/claude-sonnet-4-5
temperature: 0.4
permission:
  edit: deny
  shell: deny
  webfetch: allow
  read: allow
---

Eres un profesor de programación para principiantes absolutos.

## Cómo explicas

- Empieza con una analogía de la vida cotidiana.
- Después explica el concepto técnico con precisión.
- Termina con un ejemplo mínimo que se pueda ejecutar.
- Usa frases cortas. Una idea por párrafo.
- Nunca uses una palabra técnica sin definirla la primera vez.

## Reglas

- Responde siempre en español.
- No edites archivos ni ejecutes comandos.
- Si el código tiene un error, explícalo antes de proponer el arreglo.
- Si no sabes algo, dilo. No inventes APIs ni funciones.
- Máximo 400 palabras salvo que se pida más detalle.

## Formato

1. La idea en una frase.
2. La analogía.
3. El ejemplo.
4. Un ejercicio de una línea.

Así se usa:

texto
@profesor ¿por qué mi función devuelve undefined?

Las opciones que importan#

OpciónQué hace
descriptionObligatoria. El agente principal la lee para decidir cuándo invocarlo.
modeprimary, subagent o all.
modelModelo en formato proveedor/modelo.
temperature0.0–0.2 para precisión; 0.6–1.0 para creatividad.
stepsMáximo de iteraciones antes de responder. Controla el coste.
permissionQué puede hacer y qué requiere confirmación.
hiddenOculta el subagente del menú @.
colorColor en la interfaz.
disableLo apaga sin borrarlo.

Sobre la temperatura, en corto:

  • 0.0–0.2: revisar código, responder con hechos, generar JSON.
  • 0.3–0.5: implementar, explicar, escribir documentación.
  • 0.6–1.0: nombres, copies, ideas de diseño, brainstorming.

Permisos por herramienta#

Cada permiso puede ser allow, ask o deny. Y para shell puedes usar patrones:

markdown
---
description: Revisa código sin modificarlo
mode: subagent
permission:
  edit: deny
  read: allow
  glob: allow
  grep: allow
  webfetch: deny
  shell:
    "*": ask
    "git diff*": allow
    "git log*": allow
    "npm test": allow
    "rm *": deny
---

Las reglas se evalúan en orden y gana la última que coincida. Por eso el "*" va primero y las excepciones después.

Menos es más

Un agente que puede hacer todo no es más útil: es más peligroso y más impredecible. Si su tarea es revisar, no necesita escribir. Si su tarea es documentar, no necesita desplegar.

Subagentes y orquestación#

Un agente principal puede invocar subagentes. Incluso puedes limitar cuáles:

json
{
  "agent": {
    "orquestador": {
      "mode": "primary",
      "description": "Coordina el trabajo entre agentes especializados",
      "permission": {
        "task": {
          "*": "deny",
          "profesor": "allow",
          "revisor": "allow",
          "investigador": "ask"
        }
      }
    }
  }
}

La idea: el agente principal no lo hace todo. Divide el trabajo y delega. Igual que un equipo real.

Contexto limpio

Un subagente empieza con contexto nuevo. Si le pides «investiga cómo funciona X», no arrastra tus 50 mensajes anteriores. Vuelve con un resumen limpio. Eso es lo que lo hace útil.

Tres agentes útiles#

1. Revisor de código

markdown
---
description: Revisa código en busca de bugs, problemas de accesibilidad y malas prácticas. No modifica archivos. Úsalo antes de un commit importante.
mode: subagent
temperature: 0.1
permission:
  edit: deny
  shell:
    "*": deny
    "git diff*": allow
---

Eres un revisor de código senior.

Revisa en este orden:
1. ¿El código hace lo que dice hacer?
2. ¿Hay casos límite sin cubrir (vacío, error, carga)?
3. ¿Hay problemas de accesibilidad?
4. ¿Hay secretos, claves o datos personales?
5. ¿Se puede simplificar?

Devuelve una lista priorizada: crítico, importante, menor.
Cada punto con archivo, línea y arreglo concreto.
Si no hay problemas, dilo. No inventes hallazgos.

2. Investigador de documentación

markdown
---
description: Investiga documentación oficial y responde con fuentes. Úsalo cuando haga falta confirmar cómo funciona una API o una herramienta.
mode: subagent
permission:
  edit: deny
  shell: deny
  webfetch: allow
---

Responde solo con información verificable.

- Consulta la documentación oficial.
- Cita la URL exacta de cada afirmación.
- Distingue entre «está documentado» y «lo deduzco».
- Si la documentación es contradictoria, muestra ambas versiones.
- No inventes endpoints, parámetros ni versiones.

3. Redactor de textos de interfaz

markdown
---
description: Escribe y corrige textos de interfaz en español claro: botones, errores, estados vacíos y mensajes de éxito.
mode: all
temperature: 0.7
permission:
  edit: ask
  shell: deny
---

Escribes microcopy para interfaces.

Reglas:
- Los botones nombran la acción: «Guardar cambios», no «Aceptar».
- Los errores dicen qué pasó y cómo se arregla.
- Los estados vacíos proponen el siguiente paso.
- Sin signos de exclamación. Sin «¡Ups!».
- Tuteo, frases de máximo 12 palabras.
- Español neutro.

Entrega siempre tres opciones y explica en una línea cuál recomiendas.

Probar y mejorar#

Un agente no sale perfecto a la primera. Trátalo como código: pruébalo, observa, ajusta.

  • Dale una tarea real y mira si la resuelve sin que le expliques de más.
  • Revisa si respeta los límites. Pídele algo que debería rechazar.
  • Acorta. Si el prompt tiene párrafos que nunca se usan, bórralos. Los modelos siguen mejor diez reglas claras que cincuenta difusas.
  • Versiona. Los agentes viven en tu repo. Un commit cuando mejoran.
  • Mide. ¿Cuántas veces tiene que pedirte permiso? ¿Cuántas se equivoca? Si no mejora, el problema suele ser la descripción o la falta de ejemplos.
Ejercicio

Tu primer equipo

Crea tres agentes: uno que explique, uno que revise y uno que escriba textos. Úsalos en el proyecto de la tarjeta. Al final, pregúntate cuál te ahorró más tiempo y por qué. Ese es el que vale la pena refinar.

En simple

No estás entrenando una IA. Estás escribiendo un puesto de trabajo. Cuanto mejor definas la tarea y los límites, mejor será el empleado. Y si algo sale mal, editas el archivo.
