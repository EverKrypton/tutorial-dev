Lo que no cuenta el tutorial de cinco minutos

Publicar una página es fácil. Mantenerla viva es donde aparecen las decisiones: qué corre en el servidor, cómo se guardan los secretos, qué pasa cuando el tráfico sube, cómo vuelves atrás cuando algo se rompe.

Este capítulo es Vercel en serio, después de que ya sabes desplegar.

Los tres modelos de ejecución

Antes de escribir código, decide dónde vive:

ModeloQué esCuándoLímite
EstáticoHTML y assets en la CDNContenido que no cambia por usuarioNinguno relevante
ServerlessUna función que arranca por peticiónAPI, formularios, datos privadosTimeout, arranque en frío
EdgeFunción en el nodo más cercanoRedirecciones, geolocalización, A/BAPIs limitadas, sin filesystem

La regla práctica: estático por defecto, serverless cuando hay datos privados, edge solo si la latencia es el problema.

En simple

Estático es un cartel pegado en la pared: se sirve igual a todos y no cuesta nada. Serverless es un empleado que atiende pedidos: cobra por pedido y tarda un segundo en despertar. Edge son sucursales en cada ciudad: rapidísimo, pero con menos herramientas.

Funciones que aguantan producción

Una ruta de API ingenua se rompe con el primer caso raro. Esta es la versión que sí aguanta:

ts
// app/api/suscribir/route.ts
import { NextResponse } from "next/server";

export const runtime = "nodejs";
export const maxDuration = 10;

export async function POST(req: Request) {
  try {
    const body = await req.json().catch(() => null);
    const email = typeof body?.email === "string" ? body.email.trim() : "";

    if (!/^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(email)) {
      return NextResponse.json({ error: "Correo inválido" }, { status: 400 });
    }

    const res = await fetch("https://api.proveedor.com/suscribir", {
      method: "POST",
      headers: {
        "Content-Type": "application/json",
        Authorization: `Bearer ${process.env.PROVEEDOR_KEY}`,
      },
      body: JSON.stringify({ email }),
    });

    if (!res.ok) {
      console.error("proveedor falló", res.status, await res.text());
      return NextResponse.json({ error: "No pudimos completar la suscripción" }, { status: 502 });
    }

    return NextResponse.json({ ok: true }, { status: 201 });
  } catch (e) {
    console.error("error inesperado", e);
    return NextResponse.json({ error: "Error interno" }, { status: 500 });
  }
}

Cuatro cosas que hacen la diferencia:

  • Valida la entrada antes de usarla, y devuelve 400 con un mensaje concreto.
  • Nunca devuelvas el error crudo del proveedor al cliente: regístralo tú.
  • Distingue 400 (culpa del cliente) de 500 (tuya) de 502 (del proveedor).
  • Pon un maxDuration explícito en vez de confiar en el default.

Secretos y entornos

Vercel tiene tres entornos: Production, Preview y Development. Una variable puede existir en uno y no en otro, y ese es el error número uno de los deploys que «funcionan en preview».

bash
vercel env ls
vercel env add STRIPE_KEY production
vercel env pull .env.local

# cambiar una y volver a desplegar (las variables no se recargan solas)
vercel --prod
Rotar una clave

Si una clave se filtra: revócala en el proveedor, crea una nueva, actualiza la variable en Production y Preview, redespliega y comprueba los logs. Borrarla del código no basta: sigue en el historial de Git.

Previews: el flujo de trabajo de verdad

Cada push a una rama o PR genera una URL única con su propio entorno. Ese es el mecanismo que permite revisar sin tocar producción.

flujo
git switch -c feat/precios
# ...trabajas...
git commit -am "feat: nueva tabla de precios"
git push -u origin feat/precios
# Vercel comenta la URL de preview en el PR
# se revisa, se aprueba, se mezcla a main → producción

Dos ajustes que conviene hacer desde el principio:

  • Protección de previews: que solo tu equipo pueda verlas si el proyecto no es público.
  • Base de datos separada por entorno: nunca apuntes un preview a la base de datos de producción.

Tareas programadas

Con un vercel.json puedes ejecutar una ruta cada cierto tiempo, sin servidor propio:

json
{
  "crons": [
    { "path": "/api/limpiar", "schedule": "0 3 * * *" },
    { "path": "/api/informe", "schedule": "0 9 * * 1" }
  ]
}

Y la ruta se protege con el secreto que Vercel inyecta:

ts
export async function GET(req: Request) {
  if (req.headers.get("authorization") !== `Bearer ${process.env.CRON_SECRET}`) {
    return new Response("No autorizado", { status: 401 });
  }
  // trabajo real
  return Response.json({ ok: true });
}
Cron no es un servidor

Las tareas programadas tienen límite de duración. Si necesitas procesar algo de veinte minutos, divídelo en trozos, usa una cola o un servicio de workflows. Un cron no es un daemon.

La diferencia entre una web rápida y una lenta casi siempre es caché bien puesta.

const res = await fetch(url, { next: { revalidate: 60 } });

Observar: logs y métricas

Lo que no mides no lo puedes arreglar. Lo mínimo:

  • Logs de función: en el panel del deployment o con vercel logs. Los console.log del servidor aparecen aquí, no en el navegador.
  • Web Vitals: LCP (carga), INP (respuesta), CLS (estabilidad visual). Son las tres que siente el usuario.
  • Errores: conecta Sentry o similar. Un error en producción sin traza es un misterio eterno.
  • Uso: vercel usage para no llevarte una sorpresa en la factura.
bash
vercel logs https://mi-app.vercel.app
vercel inspect https://mi-app.vercel.app --logs
vercel usage

Cuando algo se rompe

El plan, en orden, sin pánico:

  1. Rollback inmediato

    Promociona el deployment anterior desde el panel. Treinta segundos y el sitio vuelve a funcionar.

  2. Lee los logs

    Qué función, qué línea, qué código de estado. Sin eso, estás adivinando.

  3. Reproduce en preview

    El fallo casi siempre se reproduce en un preview de la rama.

  4. Arregla con un commit pequeño

    Un cambio, una causa. No mezcles el arreglo con una refactorización.

  5. Anota

    Qué pasó y cómo se detectó. La próxima vez se detecta antes.

Checklist de producción

  • Todas las variables existen en Production y en Preview.
  • Ninguna clave tiene prefijo público.
  • Cada ruta de API valida la entrada y distingue códigos de estado.
  • Los errores se registran en el servidor; el cliente recibe un mensaje útil.
  • Hay un estado de carga y un estado de error en cada vista con datos.
  • El sitio funciona con JavaScript desactivado en las páginas de contenido.
  • Probado en un teléfono real, no solo en el emulador.
  • Sabes cómo hacer rollback y lo has practicado una vez.
  • Web Vitals medidos con datos reales, no solo en tu máquina.
Lo importante

Desplegar es el principio, no el final. Un proyecto profesional se define por lo que pasa cuando algo falla: si puedes volver atrás en treinta segundos y sabes leer los logs, estás por encima de la mayoría.
